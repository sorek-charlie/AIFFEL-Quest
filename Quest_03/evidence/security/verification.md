# 로컬 보안 검증 · 2026-10-29

최신 0.2: 실행 키만으로 로그인할 수 없으며 첫 비밀번호 설정에만 실행 키를 사용합니다. scrypt 해시 저장·6회 실패 잠금·비밀번호 변경 후 모든 기존 세션 무효화·재시작 보존을 테스트했습니다. Google PKCE·일회성 state와 기존 세션 연결, 지정 계정 외 연결 거부를 가상 응답으로 테스트했습니다. 실제 Google 계정 권한 검증은 아직 하지 않았습니다. Android는 알림 접근 및 캘린더 권한을 사용자가 직접 부여해야 하며, 기본 수집 꺼짐·확인 후 저장·앱 데이터 백업 꺼짐·네트워크 권한 없음으로 구성했습니다. 실제 기기 권한 시험은 미실행입니다.

아래는 비밀번호 도입 전 초기 로컬 세션 구현의 검증 기록입니다. 현재 로그인은 비밀번호가 필요합니다.

`tests/integration/scheduler.test.mjs` 실행 결과:

- 사용자 A가 저장한 할 일을 사용자 B가 조회할 수 없으며 타인 ID 삭제 404.
- 같은 DB의 두 API 인스턴스에서 각자의 실행 키와 세션을 발급. A 세션을 B 서버에 사용하면 401.
- 쿠키 없는 owner 조회 401. 외부 Origin으로 쓰기 요청 403.
- 공개 프로필 응답에 발신 번호와 개인 일정 제목 없음.
- 잘못된 상태 capability와 타인 요청 ID는 404.
- SQLite 파일에 원문 상태 capability가 포함되지 않음. 멱등성 응답은 AES-GCM으로 암호화.
- 동시 승인 한 건만 성공. 같은 승인 재시도로 일정 중복 생성 없음.

production 실행 거부, loopback bind, Host 검사, 요청 크기 제한, 프로세스 내 rate limit을 구현했습니다.
로컬 실행 키는 URL fragment로 전달하고 로그인 전에 주소창에서 제거합니다. 세션은 HttpOnly/SameSite=Strict이며 로컬 HTTP이므로 Secure 속성은 적용하지 않습니다.
개인 사용 PC의 OS 계정 보안과 데이터 폴더 접근 제어를 대체하지 않습니다.

Supabase RLS·클라우드 인증·외부 보안 스캐너: 실행 안 함. 해당 기능은 미구현입니다.
