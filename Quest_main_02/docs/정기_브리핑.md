# 정기 브리핑 설계

상태: 가상 데이터 기반 출력기와 수동 Telegram 전송 명령을 구현했다. 공공 API·뉴스 수집, 로컬 LLM과 자동 스케줄러는 연결되지 않았다. 첨부 노트는 제안이며, 사용자가 뒤에 확정한 내용이 우선한다.

## 확정된 보고

| | 일간 이슈 | 주간 정부정책 |
|---|---|---|
| 발송 | 매일 09:00 KST | 월요일 09:00 KST |
| 수집 | 수집 시각 미정 | 매일 08:30 KST (자동 수집 구현 전) |
| 범위 | AI·경제·정치·사회·기술·주식 | 중소기업, 서울·경기 중심 |
| 요약 모델 | 로컬 LLM 기본 | 로컬 LLM 기본 |
| 채널 | Telegram | Telegram |

## 출력

### 사용자 제공 HTML 스냅샷

2026-11-16에 저장된 전국·경기 주간 안내 HTML을 `briefing-data` JSON만 읽어 분석한다. HTML/JavaScript는 실행하지 않는다. 2026-11-17을 기준으로 주간 목록 42건 중 마감 2건을 제외한 40건(전국 21, 경기 19)을 표시하며, 7건은 마감일 필드가 비어 있다. 이는 원문을 실시간으로 검증한 결과가 아니다. 별도 `all` 목록은 844건이다. 소상공인·중소기업·지역 등 실제 대상은 공고 원문 확인이 필요하다. 스냅샷은 서울 전용 목록이나 이후 신규 공고를 포함한다고 가정하지 않는다.

웹의 정부정책 메뉴에서 제공된 스냅샷 결과 링크를 열거나 다른 HTML 파일을 가져와 스캔할 수 있다. 파일 자체는 정적 저장본이므로 매일 같은 파일을 다시 읽어도 새 공고가 자동 수집되지 않는다. 자동 수집은 별도 실시간 출처와 인증이 필요하다.

일간: 생성 시각과 대상 기간, 분야별 제목·핵심 내용·출처·게시 시각·원문 링크. 투자 자문이나 가격 전망으로 보이는 표현은 피하고 사실/해석을 구분한다. 수집 실패와 누락 분야를 명시한다.

주간: 생성 시각·수집 기간, 공고 제목, 기관, 대상/지역, 지원 내용, 접수 기간, 원문 링크, 신규/변경 여부, 원문 검증 상태와 수집 실패. 지원 자격·금액·기한이 없거나 대조되지 않으면 `확인 필요`로 표시한다. 전국 공고 포함 여부, 대상 세부 조건, 우선순위·정렬, 항목 수는 미결정이다.

`python -m briefings.render --kind policy --input examples/policy.json` 및 `--kind issue --input examples/issue.json`으로 메시지 형식을 로컬에서 볼 수 있다. 데이터는 가상이며 미리보기 출력기는 `source_checked` 입력을 그대로 표시한다. 자동으로 원문을 확인하지 않는다. 메시지가 3,800자를 넘으면 잘라내지 않고 오류로 반환한다.

수동 발송은 `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`를 실행 환경변수로 설정한 후 `python -m briefings.send --kind policy --input <검토한_JSON>`을 사용한다. 예제·빈 보고서·출처/유효 URL 누락·원문 미대조·출처 실패 보고서는 발송되지 않는다. 검토 여부는 입력자가 표시하며 실제 원문 대조를 보장하지 않는다. 사용자에게 확인되지 않은 부분 발송 정책 때문에 현재는 실패 출처가 있으면 보류한다. 데이터 수집, 파일 전달 및 스케줄러는 미구현이다. DB `data/briefing-delivery.sqlite3`는 같은 종류·날짜의 중복 발송을 방지하며 `unknown`은 실제 채팅에서 확인해야 한다. 해당 수동 명령은 이미 존재하는 JSON을 실제 외부 Telegram에 보낸다. `.env.example`은 키 목록이며 프로그램이 `.env`를 자동으로 읽지는 않는다.

## 수집·검증·발송 설계

1. 실행별 `report_kind + 예정일(KST)`과 고유 run_id를 기록한다. 한 날짜에 두 보고를 별도 작업으로 처리한다.
2. 선정된 출처의 게시물·원문과 URL, 시각, 출처별 성공·실패를 수집한다. 기업마당·판판대로는 후보이며 API 승인·실제 필드·이용 조건 확인 전 확정하지 않는다. 이슈 출처도 미정이다.
3. 공고 ID 및 정규화 URL/콘텐츠 기준으로 중복과 변경 이력을 구분한다. 원문 저장 시 자료의 이용 조건을 확인한다.
4. 날짜·지원금액·대상·지역·링크 등 핵심 필드를 원문과 대조한다. 대조 실패·누락은 `확인 필요`로 표시하고 임의 보완하지 않는다. LLM 출력은 신뢰하지 않는 외부 텍스트에서 추출한 초안으로 취급하고, 숫자·문맥은 별도 검증한다.
5. 실패한 소스별 상태와 검증 결과를 남기고, 사람이 볼 수 있는 보고서를 구성한다. 부분 발송/보류, 재시도 횟수, 정체 판단은 설정이 확정되기 전 결정하지 않는다. 첨부 문서의 3회 재시도는 제안이다.
6. Telegram은 Bot API `sendMessage`와 필요한 경우 `sendDocument`를 사용한다. 승인된 채팅에만 발송하고 토큰은 환경변수로 관리한다. 발송 요청 전 상태를 기록하고 응답의 message_id를 저장한다. 네트워크 중단 등으로 성공 여부가 불분명하면 `unknown`으로 남겨 자동 재전송을 막는다. 서비스가 보장하지 않는 정확히 한 번 발송은 약속하지 않는다. 메시지 분할은 서버 제한을 확인해 구현하며 누락을 숨기지 않는다.
7. 예약 시각과 시간대 및 PC 가동 상태를 기록한다. PC가 꺼져 있던 실행의 지연 발송/건너뛰기와 공휴일 처리, 개인 채팅/그룹은 사용자 결정이 필요하다.

## 검증 가능한 결과와 중단 기준

- 표본의 공고 날짜·금액·링크와 원문을 대조해 정확도·누락·틀린 자격 판정을 기록한다. 정답 데이터와 수작업 소요 시간은 수집 전이므로 목표 수치는 미정이다.
- 실행 로그: 실행일·수집 기간, 원본별 성공/오류, 중복·필터 수, 검증 실패, 모델 버전·처리 시간, 발송 상태·오류. 비밀키나 불필요한 개인정보는 제외한다.
- 생성과 검증을 분리한다. 소스 미수집, 링크·날짜 검증 실패, 모델 출력 형식 오류, 모든 소스 실패 등 중단·부분 처리 조건은 명시적으로 정하고 기록한다.
- 월간 예산 상한과 재시도 상한은 설정 가능하도록 설계하되 금액과 횟수는 미확정이다. 로컬 기본 경로는 유료 호출을 전제하지 않는다.
- 단일 출처 오류, 중복 공고, 마감 지난 공고, 원문 수치 불일치, 소스 전체 실패, 주말·공휴일, 재시작·발송 결과 불명, 텔레그램 길이 제한을 테스트한다.
